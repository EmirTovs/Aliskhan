# CandleFlow AI — Frontend

Современный веб-интерфейс системы управления производством свечей. Frontend построен на **React**, **TypeScript** и **Vite** и взаимодействует с backend через REST API. AI-ассистент также работает через backend: браузер не обращается к OpenAI напрямую и не хранит секретный API-ключ.

> **Статус проекта:** frontend-часть приложения. Для полноценной работы требуется запущенный CandleFlow AI backend и настроенная база данных. Наличие интерфейса AI-ассистента не означает, что OpenAI API уже оплачен или доступен: доступность AI зависит от конфигурации backend и состояния API-баланса.

## Возможности интерфейса

В приложении предусмотрены следующие функциональные разделы:

| Раздел | Назначение |
|---|---|
| Dashboard | Сводная панель и переходы к основным разделам |
| Materials | Работа со справочником материалов |
| Suppliers | Управление поставщиками |
| Batches | Просмотр и управление партиями сырья |
| Recipes | Работа с рецептурами |
| Production | Просмотр и управление производственными заданиями |
| AI Assistant | Диалог с AI-ассистентом через backend API |
| Authentication | Вход пользователя и получение пользовательской сессии |

Набор доступных действий определяется текущей реализацией frontend и возможностями backend API. Бизнес-правила, расчёты остатков, резервирование партий, производственные операции и интеграция с OpenAI должны выполняться на backend, а не дублироваться в браузере.

## Технологический стек

- **React** — компонентный пользовательский интерфейс.
- **TypeScript** — статическая типизация.
- **Vite** — локальный dev-сервер и production-сборка.
- **Lucide React** — иконки.
- **Recharts** — визуализация данных и графики.
- **CSS** — стили интерфейса и адаптивная раскладка.
- **Fetch API** — HTTP-взаимодействие с backend.

Версии зависимостей задаются в `package.json` и фиксируются файлом `package-lock.json`. Для воспроизводимой установки используйте `npm ci`.

### Принципы организации кода

1. **Разделение по функциям.** Код материалов находится в `features/materials`, код производства — в `features/production` и т. д.
2. **Общие элементы не дублируются.** Повторно используемые элементы интерфейса располагаются в `components/ui`.
3. **Общая инфраструктура отделена от страниц.** API-клиент и общие типы находятся в `shared`.
4. **Корневая оболочка управляет компоновкой.** `app/App.tsx` отвечает за проверку пользовательской сессии, отображение навигации и выбор активного раздела.
5. **Backend остаётся источником бизнес-логики.** Frontend отображает данные и отправляет команды API; он не должен самостоятельно принимать критичные решения о запасах или производстве.

> Структура подготовлена для дальнейшего выделения отдельных компонентов, hooks и сервисов внутри feature-модулей по мере роста функциональности. Не следует считать пустые директории `components/layout` или `pages` уже реализованными модулями.

## Переменные окружения

Frontend использует следующую переменную:

| Переменная | Обязательность | Пример | Описание |
|---|---:|---|---|
| `VITE_API_URL` | Нет | `http://127.0.0.1:8000/api/v1` | Базовый URL backend API |

Если `VITE_API_URL` не задана, API-клиент использует значение по умолчанию `http://127.0.0.1:8000/api/v1`.

**Важно:** Vite встраивает переменные с префиксом `VITE_` в клиентский bundle. Поэтому в frontend `.env` допустимы только публичные настройки. Не добавляйте туда `OPENAI_API_KEY`, пароли PostgreSQL, Redis, JWT-секреты или другие серверные секреты.

После изменения `.env` перезапустите dev-сервер. Для production-сборки переменные окружения должны быть заданы на этапе `npm run build`.

## Связь с backend

Общий HTTP-клиент находится в:

```text
src/shared/api/client.ts
```

Он:

- формирует запросы к `VITE_API_URL`;
- добавляет `Content-Type: application/json`;
- добавляет `Authorization: Bearer <token>`, если токен пользовательской сессии сохранён;
- обрабатывает HTTP `204 No Content`;
- преобразует тело ошибки API в JavaScript `Error`.

Пример использования:

```tsx
import { api } from '../../shared/api/client';

type Material = {
  id: string;
  name: string;
};

const materials = await api<Material[]>('/materials');
```

Пути в вызовах `api()` указываются относительно базового префикса `VITE_API_URL`. Если переменная заканчивается на `/api/v1`, передавайте `/materials`, а не `/api/v1/materials`.

### CORS

Если frontend и backend работают на разных origin (домен, протокол или порт отличаются), backend должен разрешать origin frontend в настройках CORS.

Например, локальная разработка обычно использует:

- frontend: `http://localhost:5173`;
- backend: `http://127.0.0.1:8000`.

Разрешённые адреса нужно настроить на backend. Не используйте разрешение всех origin в production без отдельного обоснования.

## Авторизация и хранение токена

Текущий API-клиент предоставляет функции:

```tsx
import { getToken, setToken } from './shared/api/client';

setToken('access-token'); // сохранить токен
const token = getToken(); // получить токен
setToken(null);            // удалить токен
```

Токен сохраняется в `localStorage` под ключом `cf_token`. При API-запросах он передаётся в заголовке `Authorization: Bearer ...`.

При старте приложения выполняется проверка сохранённой сессии через:

```text
GET /auth/me
```

Если токен отсутствует или проверка не проходит, приложение возвращает пользователя к экрану входа.

Учитывайте, что `localStorage` доступен JavaScript-коду страницы. Для production-системы с повышенными требованиями к безопасности можно рассмотреть серверную сессию и cookie с флагами `HttpOnly`, `Secure` и `SameSite` — такая схема требует согласованных изменений backend.

## AI-ассистент

AI-ассистент расположен в модуле:

```text
src/features/assistant/pages/AssistantPage.tsx
```

Frontend обращается к backend API и не вызывает OpenAI непосредственно из браузера.

Используемые маршруты backend (относительно `/api/v1`):

| Метод | Endpoint | Назначение |
|---|---|---|
| `GET` | `/ai/conversations` | Получение списка диалогов |
| `GET` | `/ai/conversations/{conversation_id}/messages` | Получение сообщений диалога |
| `DELETE` | `/ai/conversations/{conversation_id}` | Удаление диалога на стороне API |
| `POST` | `/ai/chat/stream` | Отправка сообщения и получение ответа через SSE |
| `POST` | `/ai/confirm-production-plan` | Подтверждение плана производства |

Доступ к защищённым маршрутам выполняется с Bearer-токеном пользовательской сессии.

### Поток ответа

1. Пользователь отправляет сообщение из интерфейса.
2. Frontend отправляет запрос на backend.
3. Backend проверяет пользователя и обрабатывает запрос.
4. Backend взаимодействует с OpenAI API, если это предусмотрено серверной логикой.
5. Frontend отображает полученный ответ и историю диалога.

**OpenAI API key должен храниться только в окружении backend.** Не добавляйте его в `VITE_*` переменные и не помещайте в исходный код frontend.

### Ошибки OpenAI

Ошибки `401`, `404` и `429`, возвращаемые backend, относятся к настройке или доступности OpenAI API:

- `401` — неверный или недействительный API-ключ;
- `404` — указанная модель недоступна или идентификатор модели неверен;
- `429` — исчерпан лимит, баланс или доступная квота API.

Проверяйте ключ, модель, лимиты и биллинг на стороне OpenAI Platform и backend. Не пытайтесь исправлять такие ошибки публикацией API-ключа во frontend.

## Сборка и публикация

### Production-сборка

Перед сборкой укажите production URL backend в `.env`:

```env
VITE_API_URL=https://api.example.com/api/v1
```

Затем выполните:

```bash
npm ci
npm run build
```

Vite создаст статические файлы в `dist/`. Их можно разместить на статическом веб-сервере или отдавать через Nginx.

### Пример конфигурации Nginx

Ниже пример для SPA, если собранные файлы находятся в `/var/www/candleflow/frontend/dist`, а backend доступен локально на `127.0.0.1:8000`.

```nginx
server {
    listen 80;
    server_name candleflow.example.com;

    root /var/www/candleflow/frontend/dist;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_buffering off;
        proxy_read_timeout 300s;
    }
}
```

`proxy_buffering off` и увеличенный `proxy_read_timeout` полезны для маршрутов, использующих SSE. Проверьте фактическую схему URL backend и настройте `proxy_pass` соответственно. Если API размещён на отдельном поддомене, настройте отдельный server block и корректный CORS на backend.

Для HTTPS настройте TLS-сертификат (например, через Let's Encrypt / Certbot) и перенаправление HTTP на HTTPS.

> Конфигурация выше — пример, а не готовый универсальный deployment-файл. Пути, домены, TLS и адрес backend нужно адаптировать под инфраструктуру проекта.

## Разработка и соглашения

### Добавление нового функционального раздела

Для новой области создайте feature-модуль:

```text
src/features/new-feature/
├── pages/
├── components/
├── hooks/
├── services/
└── types/
```

Добавляйте только действительно необходимые каталоги. Не создавайте пустые слои ради формального соблюдения структуры.

Рекомендуемое разделение ответственности:

- `pages/` — композиция страницы и связывание компонентов;
- `components/` — UI-компоненты конкретной функции;
- `hooks/` — переиспользуемая React-логика;
- `services/` — запросы и сценарии взаимодействия с API;
- `types/` — типы, относящиеся к конкретному feature.

Общие компоненты и инфраструктуру размещайте в `components/` и `shared/`, если они действительно используются несколькими модулями.

### Именование

- React-компоненты и файлы компонентов — `PascalCase`: `MaterialsPage.tsx`;
- функции и переменные — `camelCase`;
- типы и интерфейсы — `PascalCase`;
- CSS-классы — осмысленные имена, привязанные к компоненту или блоку.

### Работа с API

- Не размещайте `fetch`-логику в больших JSX-разметках.
- Используйте общий API-клиент.
- Типизируйте ответы backend.
- Обрабатывайте состояния загрузки, пустых данных и ошибок.
- Не переносите в frontend бизнес-правила, которые должны быть гарантированы backend.

## Диагностика проблем

### Frontend не может подключиться к backend

1. Убедитесь, что backend запущен.
2. Проверьте URL в `.env`.
3. Проверьте доступность backend, например открыв его Swagger UI.
4. Проверьте CORS на backend.
5. После изменения `.env` перезапустите Vite.

### Ошибка `401 Unauthorized`

Проверьте пользовательскую авторизацию и срок действия access token. Это не то же самое, что ошибка `401` от OpenAI: frontend использует собственный Bearer-токен для backend API.

### Ошибка `404 Not Found`

Проверьте `VITE_API_URL`, API prefix и существование маршрута на backend. Убедитесь, что префикс `/api/v1` не продублирован.

### Ошибка CORS

Добавьте точный origin frontend в разрешённые origins backend. Origin включает протокол, домен и порт.

### AI-ассистент возвращает ошибку OpenAI

Проверьте серверные `OPENAI_API_KEY`, `OPENAI_MODEL`, доступность модели и состояние биллинга OpenAI API. Не публикуйте секретный ключ в GitHub, issue или чате.

### Ошибка сборки TypeScript

Выполните:

```bash
npm ci
npm run build
```

Исправьте ошибки типов и импорта, затем повторите сборку. Не заменяйте проверку типов отключением TypeScript или подавлением ошибок без понимания причины.

## Безопасность

- Не коммитьте `.env`.
- Не добавляйте секреты в переменные `VITE_*`.
- Не храните OpenAI API key в браузере.
- Не отключайте проверку TLS в production.
- Настраивайте CORS на backend по принципу минимально необходимых origin.
- Не считайте скрытие кнопки в интерфейсе контролем доступа: права должны проверяться backend.
- Не логируйте access token и секретные данные пользователя.
- Используйте HTTPS в production.
